# Experimental Resources Department — PoC Phase 1

Scope: isolated setup, seven real synthetic artifacts, authored truth, five fixture
accounts and twenty future RAG cases. No OCR/extraction pipeline, embeddings,
model requests, application routes or document/RAG modules run here. The generator
authors files from known text; setup tests inspect their structure, not OCR quality.
Fixture accounts have fresh Argon2 hashes and private generated passwords; they
are **not** enrolled in Core and there is no PoC login API in Phase 1.

## Independent resources

- Standalone Compose file, one digest-pinned PostgreSQL 17 container, private internal network,
  no host ports and a new project-scoped named volume for every run.
- `poc_registry`: synthetic department/user profiles and private password hashes.
- `poc_experimental`: metadata-only fixture catalog and D1 transition events.
- Separate restricted LOGIN roles: registry app and tenant app. Neither can connect
  to the other database, create schemas/tables, inherit administrative roles or read
  the bootstrap secret through SQL. Registry runtime cannot read password hashes.
- `poc_owner` is NOLOGIN. Bootstrap is privileged only inside this new cluster and
  is never supplied to an API. There is no API in this phase.
- Nothing imports the application engine, dotenv, original database registry,
  existing HR/Finance/Legal volumes or provider configuration. Inherited PG/DB/
  provisioning/provider-secret variables are stripped from child processes.

## Install and create files (repository root, PowerShell 7.2+)

```powershell
python -m venv .local/poc1-venv
.local/poc1-venv/Scripts/python.exe -m pip install -r poc/phase1/requirements.txt
.local/poc1-venv/Scripts/python.exe poc/phase1/generate.py
.local/poc1-venv/Scripts/python.exe -m pytest -c poc/phase1/pytest.ini --confcutdir=poc/phase1 poc/phase1/tests -q -p no:cacheprovider
```

Generated artifacts and ground-truth.json are committed public **synthetic** data.
The generator fixes document metadata where practical and emits SHA-256/byte sizes
for exactly the generated bytes. ZIP/PDF library output can differ across runtimes;
reproduce the semantic dataset with pinned dependencies, then regenerate hashes.
Never substitute real company files in this fixture directory. Scan PDF D2 is
image-only; there is intentionally no hidden text layer.

On Linux/macOS use `.local/poc1-venv/bin/python` instead of the Windows interpreter.
Native database verification below defaults to Windows PostgreSQL 18 binaries.

## Start a fresh Docker run

```powershell
.local/poc1-venv/Scripts/python.exe poc/phase1/control.py init
# Copy the printed 32-character run ID (not any password).
$pocRun = '<printed-run-id>'
.local/poc1-venv/Scripts/python.exe poc/phase1/control.py up --run $pocRun
.local/poc1-venv/Scripts/python.exe poc/phase1/control.py verify --run $pocRun
```

`init` generates fresh bootstrap/runtime/account passwords under ignored
`.local/poc-phase1/<run-id>/`. Windows ACLs permit the operator and SYSTEM; POSIX
directories are 0700 and initially created secret files 0600. No secret is printed,
committed or passed as a command-line value. Access the private accounts file only
locally if required; never paste it into chat/logs.

`up` accepts only a new UUID run with no existing project containers/volumes/network.
It uses an explicitly local Docker endpoint and a new empty client config, without
reading the operator's contexts or registry credentials.
It validates container ownership labels, snapshots the new empty cluster before
role/schema changes, seeds synthetic data, performs the D1 transition and checks
runtime restrictions. Every SQL database/role target is a fixed PoC constant.
An interrupted/failed run is retained; do not adopt it or reuse a volume to retry.
Create another fresh run instead. This is deliberate fail-closed collision handling.

The Docker controller supplies only generated variables and its empty env file to:

```text
docker --config <private-run>/docker-config --host npipe:////./pipe/dockerDesktopLinuxEngine compose --env-file <private-run>/empty.env -f <repo>/poc/phase1/compose.yml --project-name ai-poc1-<run-id> up -d postgres
```

Linux uses the local unix:///var/run/docker.sock endpoint. Prefer the controller to manual Compose:
manual commands omit its collision, identity, backup and verification guards. Do
not combine this Compose file with the application's files. It requires generated
POC variables and never references an external volume. No existing Docker engine
settings or protection are changed by the controller.

## Stop without deleting data

```powershell
.local/poc1-venv/Scripts/python.exe poc/phase1/control.py stop --run $pocRun
```

Only the uniquely labelled PoC PostgreSQL service is stopped. Its volume, container,
credentials, baseline dumps and verification report remain for inspection/recovery.
No down -v, prune, volume removal, recursive delete or database drop is provided.
There is no automatic resume/reseed command in this phase.

## Native setup verification if Docker is unavailable

```powershell
.local/poc1-venv/Scripts/python.exe poc/phase1/control.py init
$pocNativeRun = '<new-printed-run-id>'
.local/poc1-venv/Scripts/python.exe poc/phase1/control.py native-test --run $pocNativeRun --postgres-bin 'C:\Program Files\PostgreSQL\18\bin'
```

This initializes another entirely new cluster in that run's private directory,
binds only loopback on an allocated ephemeral port (never 5435), captures baseline
dump/global-owner/ACL artifacts, seeds/verifies the same dataset and stops it in
finally. No existing PostgreSQL service or data directory is used. Startup port
collisions fail rather than selecting an existing database. Recovery artifacts
remain private; native success is not proof that the Docker mounting path works.

## Ground truth and D1 history

ground-truth.json contains stable artifact/document/version IDs, final status,
department AND role audience, exact authored text, evidence quotes and page/row/
cell/paragraph/line locations. Test cases resolve to explicit actor profiles and
expected outcomes/evidence/forbidden artifacts. They are evaluation data, **never**
an answer-generation source or something sent wholesale to a model.

Seeding initially publishes D1-v1 and stores D1-v2 as draft. It verifies that state,
then atomically archives v1 and publishes v2, with before/after events and a unique
published-version index. Both original artifacts/metadata rows are retained. This
is a real transition in an independent fixture catalog, not production document
versioning or a modification of the document developer's schema.

TC18 (outsider reads public D1-v2) is an unresolved service requirement. The fixture
marks its shared-knowledge implementation blocker explicitly. No cross-database
CONNECT rights are granted to make it pass. See SHARED_KNOWLEDGE.md for the proposal.

## Phase boundary and safety checks

Verify the printed run ID/project and private path before running any command.
The controller refuses arbitrary run names, symlinked state and populated/colliding
resources. Baseline artifacts are `before.dump`, `globals-before.sql` and
`owners-acls-before.json`; results are in `verification.json`. A successful report
records five users, seven artifacts, D1 events and runtime permission checks.
It explicitly reports zero executed RAG questions. Setup success does not establish
90% answer accuracy, OCR quality, latency or provider cost. Those belong to later
approved phases; no provider credentials are needed or read now.

Legal remains failed/unactivated. No existing Legal, HR, Finance or central
development database is read or modified. Stop after Phase 1 and review the data,
public-knowledge proposal and setup results before implementing processing/RAG.
